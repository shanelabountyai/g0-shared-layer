| D-12 | 2026-11-05 | **Tool names use underscores** (`claims_registry`, `brand_policy`, `audience_consent`, `measurement`, `evaluation`, `observability`, `health`); the capability ids keep their dots (`claims.registry`, …) and appear in every contract as `capability`. | Tool-name rules in MCP clients and the Anthropic API allow `[A-Za-z0-9_-]` only; a dot in a tool name is refused by some hosts. |
| D-13 | 2026-11-05 | **A contract file is what the MCP client sees.** `contracts/<capability>/v1.json` holds the tool's advertised `inputSchema` and `outputSchema`, generated from the Pydantic models by `python -m shared_layer.contracts export`. `tests/contracts/golden/` pins a byte-for-byte copy. Both must match the live models or the suite fails. | One source of truth (the models), one published artifact (the JSON), one lock (the golden). n8n (G0·B) is built from the JSON. |
| D-14 | 2026-11-05 | **Every input and output carries `version` ("1")**; the output also carries `ok` and, when `ok` is false, an `error` envelope `{code, message, field?, next?: {tool, why}}`. Errors travel **inside the output schema**, not as `is_error`, so a client that validates `structuredContent` (Claude's do) never rejects a refusal. Only an unknown tool or a malformed argument is a protocol-level `is_error`. | A1's finding (bookable-appointment-service, M-015): an error placed outside the output schema reaches the model as an exception, not as something it can recover from. |
| D-15 | 2026-11-05 | **claims.registry v1 is deterministic**: a claim is `supported` when its normalized numbers match a registry entry's numbers and the two share topic words, or when it contains a registry entry's key phrase; `unsupported` when it shares topic words with an entry but its numbers contradict that entry; `needs_source` when the registry says nothing about it. When free `text` is given, only sentences that carry a number are extracted as claims; a `claims` list is checked item by item. | No model call needed; a wrong number against a known stat is the failure the registry exists to catch. Sentences without numbers are not "claims" the registry can speak to. |
| D-16 | 2026-11-05 | **brand.policy v1 is a rule engine** over seeded rules of four kinds: `phrase` (never-use list, case-insensitive), `regex` (emoji), `max_words` and `max_sentences` (post angle: one sentence, ≤25 words, on channel `post_angle`). Judgment rules in the brand voice ("never hype", "never a pitch", "specific over general") are not enforced by the engine; they are criteria of the `post_angle_v1` rubric in `evaluation`. The full verbatim `brand_voice` text is stored with the policy as `policy.text`. | Enforce what can be enforced exactly; route judgment to the judge; keep the owner's text intact. |
| D-17 | 2026-11-05 | **audience.consent fails closed**: an unknown contact, an unknown channel, a contact without a flag for that channel, or a `do_not_contact` contact is `allowed: false` with a reason. Lookup by `contact_id` or `email` (case-insensitive). | A consent check that defaults to "yes" is not a consent check. |

The caller decides what to do when `over_cap` is true; the layer never blocks a log write. | This is G1's `run_logging` rule pulled out of four prompts into one place. Blocking a log would hide the overrun. |

| D-23 | 2026-11-16 | **claims.registry: all-numbers rule (amends D-15; contract shape unchanged, still v1).** A claim is `supported` only when **every** statistic in it is backed by a registry fact for the **same metric**: the same normalized number, in a row that shares ≥2 topic words or a whole-word key phrase with the claim, and not out-scored by a different figure of that row whose clause fits the claim's clause better. A number whose clause fits another figure of the row better is a contradiction (`unsupported`, `matched_on: number`, note names both figures — e.g. "Only 5% … report any EBIT impact" vs McKinsey's 39%). A number in no matching row is `unsupported` when a row speaks to the claim, else `needs_source`. **Sample sizes are not statistics**: registry numbers come from `stat` only, never `sample` (reverses e59d071); a claim's number counts as a sample citation (neither backs nor blocks) only when it equals a row's sample count **and** is followed by the same noun ("1,993 respondents", "65 interviews"); "105 orgs", "1,993 orgs" are statistics and fail. Key phrases match on word/phrase boundaries only. A comma-grouped count ("1,993") is no longer dropped as a year. | Review of PR #1 (2026-11-16): one matching number was enough to pass a claim that also carried a wrong one, and sample sizes could support a claim. The schema did not need to change: the same three statuses, `matched_on` values and `source` carry the stricter result, so no version bump is due under D-3; consumers see stricter verdicts, not new fields. |
| D-24 | 2026-11-16 | **claims.registry governs market and research statistics, not offers or prices.** A figure is an **offer/price figure** when one of the two words before it is `save`, `saving`, `extra`, `discount`, `coupon`, `promo`, `code`, `price`, `priced`, `pricing`, `fee` or `deposit` (for a `%` or `$` figure), or it is followed by `off`, `discount`, `savings`, `cashback`, `rebate`, `/mo`, `/month`, `/yr`, `/seat`, `per month|year|seat|user` or `a month`; a bare term length next to an offer in the same clause ("for 12 months") is part of it. Offer figures are never checked against the registry. In `text` mode a sentence whose only numbers are offer figures is not extracted. In `claims` mode (one result per item, so nothing is dropped) an offer-only claim returns `supported` with `matched_on: none`, `source: null` and a note saying it is an offer figure the registry does not govern — or `matched_on: phrase` with that row when it also contains a key phrase. A claim with both an offer figure and a statistic is checked on the statistic. **Known limit:** "companies save 30% with AI" reads as an offer; a cue list cannot tell a savings stat from a discount, and the owner's copy review still applies. | opsagent review: ordinary marketing copy ("save 15% - our people and process track") came back `unsupported` and blocked. `supported`/`none`/null source is valid under the v1 schema, so no new status and no version bump; a new `not_a_claim` status would have been a contract change for every consumer. |
| D-25 | 2026-11-16 | **Correction to D-17 (D-17 left as written):** an **unknown channel is not `allowed: false`**. `channel` is a closed enum (`email\|linkedin\|sms\|phone`) in the input schema, so a call with any other channel fails input validation and comes back as a protocol-level `isError` (per D-14, "a malformed argument"), before the capability runs. An unknown contact, a contact with no flag for the channel and a `do_not_contact` contact are still `allowed: false` with a reason. Behaviour unchanged; README, the tool description and this row now say so. | Review of PR #1: the docs promised a fail-closed result for something the schema rejects earlier. Rejecting it in the schema is the stricter of the two and needs no code change. |

Applied here to `audience.consent` (D-25 wording) and `claims.registry` (D-23/D-24 wording). | The descriptions are what the calling model reads; leaving them wrong to avoid a golden diff is worse than a reviewed, description-only diff in the PR. |
